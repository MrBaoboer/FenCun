# 氛寸 · 领域规则手册

这本手册收录推荐引擎每条规则的领域依据，回答「引擎为什么这样打分、这样给喷量」。每条规则注明源码位置（文件:函数）。

## 关于证据分级（2026-07 循证重审后重写）

本手册此前用【共识】/【经验】/【假设】三级标注。这套分级被一次系统性的循证复核推翻了——问题不在于分得粗，而在于**被标成【共识】的几条恰恰是最站不住的**（详见 §1.1）。现改用下面五级，并且必须先说清一个结论：

> **香水用法领域里，没有一条规则撑得到「强证据」。**
>
> 我们对七条研究轴取证、再对其中每一条被声称为 strong/moderate 的结论做独立对抗性复核。复核后的分布是：moderate 若干、weak 居多、industry_practice 若干，另有数条被直接推翻。**strong 一条都没剩下。**
>
> 反复出现的失效模式只有一个：**物理定律说得通 ≠ 人体使用场景里有可测量的效应量。** 蒸气压随温度上升是教科书内容，但皮肤温度是被体温调节的（环境升 9℃，皮温只升约 3.5℃），再经嗅觉的 Stevens 幂律（n≈0.2–0.3）传到主观强度，只剩个位数百分比——就在最小可辨差附近。中间还隔着多组分溶液、耗尽膜、扩散稀释、观察者距离，每一步都没有人在真实用香场景里量过。

| 标记 | 含义 |
|---|---|
| 【实证·中】 | 有同行评议研究直接支持，但外推到"人在皮肤上用香水"仍有距离 |
| 【实证·弱】 | 机制成立或有零散研究，但效应量从未在人体用香场景中测量 |
| 【行业惯例】 | 业界高度一致、但找不到研究；诚实说，它就是从业者的共同经验 |
| 【文化惯例】 | 社交习惯与审美建构，**明确不是科学**，但它正是用户要的判断 |
| 【已推翻】 | 曾写在本手册里、已被证据否定的说法，保留记录以免重犯 |

**这份分级本身就是产品资产。**「反伪精确」这条红线过去只是"不要说留香 6.2 小时"，现在它有了更深的含义：**不要宣称我们的规则是科学。** 规则可以留——用户要的正是"一个懂行的人会怎么选"——但不许给它披白大褂。

数值口径：领域量一律用档位与区间，用户永远看不到「留香 6.2 小时」这类裸小数。手册中出现的小数只有一种来源，就是引擎里的代码常数，均可在指认处核对；**这些常数一律是工程取值，没有一个是实证标定出来的**。术语以仓库实现为准，速查见下表。

## 1. 环境 × 香水表现的物理规则

### 1.1 底层原理（重审后）

原手册在这里列了「四条底层原理【共识】」。复核后有两条要改写、一条要删、只有一条站得住：

| 原文 | 复核结论 |
|---|---|
| ① 温度越高，蒸气压越大，挥发越快 | **【实证·弱】方向对，量级此前被严重高估。** 关键是搞错了 ΔT 的落点：香水膜挂在**皮肤**上，而皮肤温度受体温调节——环境升 9℃，皮温只升约 3.5℃。按皮温重算，效应从"翻倍"塌缩到 20–50%；再经 Stevens 幂律传到主观强度只剩 6–13%。**不要在代码注释、文档或 UI 里引 Clausius–Clapeyron 给系数背书。** |
| ② 湿空气传导气味的体感强度高于干空气，高湿时同样的量闻起来更浓 | **【已推翻】。**「水分子把香气分子裹住、让它悬在空中散不掉」在物理上是错的。受控气候舱研究显示，20–35℃ / 30–75%RH 区间内，温湿度对健康人的嗅觉阈值、辨别与识别**均无显著影响**；少数报告有效应的那项，方向还与民间说法相反（湿→阈值更低=更灵敏）。这条曾是 §1.2 回南天规则的全部依据，已随该规则一起删除。 |
| ③ 皮肤越干，香水越挂不住；油脂能延缓挥发 | **【实证·弱】。** 2025 年在体研究确认皮肤水合度是影响香料蒸发速率的首要皮肤参数，但**作用方向依分子性质分化**：高挥发组分主要受皮肤粗糙度影响，低挥发亲脂组分才受水合度与 TEWL 影响。不能笼统说"干就挂不住"。而且这是**受试者间**差异，不是同一个人在不同天气下的**受试者内**变化——引擎不据此做任何天气规则。 |
| ④ 密闭空间气味累积，开阔通风空间气味稀释 | **成立，但它不是物理规则，是礼仪规则。** 真正的依据比空气动力学硬得多：约三分之一人群报告对香味制品有不良反应，CDC、加州公共卫生部、CCOHS 等机构有正式无香政策，医院与部分办公场所强制执行。**按这个理由写，不要按"气味累积"写**——后者会在"密闭但空无一人的房间"里给出明显错误的建议。 |

补一条复核中新确立、且分量最重的：

> **⑤【实证·中】"合不合适"高度个体化。** 同一款香与不同人体味混合后的愉悦度差异显著；人们自选的香与自身体味的混合，优于随机分配的等愉悦度香水。同一款香在不同个体皮肤上的蒸发量差异达统计显著，是留香预测中**最大的单一不确定性来源**。
>
> 工程含义有两层：一是「绝不给精确小时数」这条红线有了真正的科学理由（见 §2.3）；二是**个人反馈必须能压过通用规则**——通用规则只是先验，用户的反馈才是证据（见 §7）。

### 1.1b 明确不做的事：风速

和风天气返回了 `windSpeed`，`Context` 里也留了字段，但**引擎刻意不使用它**。这不是遗漏，是复核后的决定：

- 风既**稀释**烟羽也**输运**烟羽。下风向 1.5 m 的人可能闻到**更多**而不是更少，而天气 API 给不出相对方位。方向不可建模，规则就不可证伪；
- 唯一对题的文献（Kasting & Saiyasombati 2001）建模的是**皮肤吸收剂量学**，风速项未经变风速实验验证，更没有测过"他人感知强度"；
- 信号本身无效度：气象接口给的是 10 m 高度城市网格风，而机制里的是**皮肤表面**气流。用户多在室内、衣物遮挡手腕颈侧，站点风与体表风基本解耦；
- 最危险的一步是把「密闭场合减 1 下」改写成 airflow 驱动——那会**把一条本来诚实的礼仪规则伪装成有论文背书的物理规则**，还会在空无一人的密闭房间里给出错误建议。

**结论：不接，且不做文案。** 曾考虑退一步只在户外场合出一句提示，最终也放弃了——`Occasion` 这套枚举根本表达不了"在不在户外"（`home` 是室内、`casual` 两可），拿它当户外判据会在室内给出无依据的提示。与其加一个看起来很科学的噪声维度，不如把决定本身写清楚。

字段保留在 `Weather` / `Context` 里，**并在 `types.ts:Weather.windSpeed` 处附了完整的弃用理由**——保留它是为了让这个决定可被看见，而不是让下一个人以为这里少写了一段。

### 1.2 体感四态判定 `season.ts:feelFromWeather`

温湿度先合成一个体感，再由体感驱动打分与喷量：

| 体感 | 判定条件 | 说明 |
|---|---|---|
| 闷热潮湿 | ≥28℃ 且湿度 ≥65% | — |
| 干热 | ≥28℃ 且湿度 <65% | — |
| 寒凉 | ≤10℃ | — |
| 温和 | 其余 | 11–27℃ 的大多数日子 |

**【已推翻】原「回南天 / 梅雨」规则 `20–27℃ 且湿度 ≥85% → 闷热潮湿`，已删除。**

它曾是本仓库最自豪的"本土化"卖点，但两头都不成立：

1. 它的机制依据是 §1.1 那条已被推翻的「湿空气里气味散不掉」；
2. 更直接的问题是分档本身——22℃/90% 与 30℃/70% 被判成同一个体感，可它们**干球温差 8℃**。删掉它不需要任何复杂论证，8℃ 就够了。

（复核中曾出现一个更漂亮的论证：两者湿空气焓相差约 16 kJ/kg，回南天的焓其实接近 28℃/40% 的干热天。算术无误，但**这个论证也不该用**——焓是 HVAC 能量记账量，不是经验证的人体感知指标；ASHRAE 55 舒适度体系恰恰不以焓为轴，等焓线上两点的热感觉可以完全不同。用一个与机制无关的变量宣布"两天差不多"，是另一种伪精确。留在这里作为反面教材。）

**换上的是有依据的那一半**：回南天真正与香水相关的问题不是"热"，是**衣物与柜子里的霉潮本底气味**——香水盖不住它。这条只驱动一句文案，不进任何打分：

```
season.ts:mustyAir(tempC, humidity)  →  15℃ ≤ t ≤ 25℃ 且湿度 ≥90%
ContextBar：「这种回潮天，先闻一下要穿的那件衣服——香水盖不住霉潮的底味。」
```

用一条真的本土洞察，换掉一条假的本土规则。

配套的季节判定不只看月份：≥28℃ 一律按夏，≤6℃ 一律按冬，极端温度盖过日历（`season.ts:seasonFromDateTemp`，详见 §6.2）。

### 1.3 体感 × 香调的修正 `scoring.ts:weatherMultiplier`

天气对总分是乘性修正 W，钳位在 [0.7, 1.3]。

**先说一个曾经的硬缺陷：幽灵香调键。** 家族定义里长期写着 `resinous`、`sandalwood`、`cedar`、`watery`、`jasmine`、裸 `spicy` —— 对 1500 款主目录 + 64 个扩展分片全量统计（共 90 种真实键）后确认：**这些键在数据集里出现 0 次**，相关判定常年静默空转。代价最大的是 `resinous`：它本该代表树脂香膏，而数据集里这个家族叫 `balsamic`（208 款），于是 208 款香膏调在热天不算厚重、在冷天也不算暖调，两条规则都白写。现已全部改为真实键，并由单测 `无幽灵香调键` 锁死——引擎引用的每个 accord 都必须在真实数据集里存在。

家族定义（`scoring.ts:F`，均为数据集实有键）：

- **甜 / 美食调**：sweet、vanilla、caramel、honey、chocolate、cacao、coffee、almond、coconut、gourmand；
- **树脂琥珀**：amber、balsamic、oud、beeswax —— **与"甜"分开**，见 §5.4；
- **厚重家族** = 甜 ∪ 树脂琥珀 ∪ animalic、tobacco；
- **清爽家族**：citrus、aquatic、marine、green、aromatic、fresh、ozonic、herbal、mineral；
- **取暖判定**：amber / balsamic / warm spicy / vanilla / leather / tobacco 任一 ≥45；或 woody ≥45 且 amber / balsamic / warm spicy 最强者 ≥40。裸 woody 不算暖：「木质」是最宽的家族，干冷的香根草、干雪松并非取暖型香，必须组合判定。

**打分路径已连续化——`Feel` 枚举退化为纯文案标签**（`FEEL_ZH`、风险话术里的"又热又潮"、`WearEntry.feel` 继续用它），不再进算分：

```ts
H = clamp((tempC − 22) / 13, 0, 1)              // 热负荷：22℃ 起算、35℃ 饱和
C = clamp((15 − tempC) / 13, 0, 1)              // 冷负荷：15℃ 起算、2℃ 饱和
M = H > 0 ? clamp((humidity − 60) / 30, 0, 1) : 0   // 闷指数：仅在有热负荷时生效

厚重家族 ≥50  → × (1 − 0.13·H − 0.06·M)
清爽家族 ≥45  → × (1 + 0.12·H)
取暖型        → × (1 + 0.12·C)
清冽 ≥50 非暖 → × (1 − 0.08·C)
W = clamp(乘积, 0.7, 1.3)
```

**为什么必须连续化。** 原来的离散分档制造了三处真实可感的断崖，而且方向恰好是错的：

| 断崖 | 旧（离散） | 新（连续） |
|---|---|---|
| 27.9℃ → 28.0℃ | 0.96 → **0.88**（0.1℃ 换 8 个百分点） | 0.9210 → 0.9200 |
| 28℃ 的 64% → 66% | 0.88 → **0.84** | 0.9320 → 0.9280 |
| **28℃ vs 34℃** | **0.88 = 0.88（完全塌缩）** | 0.9200 → **0.8600** |
| 10.1℃ → 10.0℃ | 1.05 → **1.15** | 1.0452 → 1.0462 |

第三行是最没道理的一处：**温度是本轮循证里唯一方向可靠的变量，却恰恰在最需要区分的高温段被离散化抹平了。** 而且这与本仓库自己的既定原则冲突——`occasionFit` 的注释写着「连续函数，不设悬崖，60/61 之间不许出现 0.03 级的总分跳变」。同一份代码不该两套标准。单测 `天气乘子连续化` 锁死了阈值两侧的连续性、高温段的单调性与不塌缩。

**关于那些系数【全部是启发式】。** 22/35/15/2℃、60/90%、0.13/0.06/0.12/0.08 —— 没有一个有实证依据。断点的选取原则不是"更准"，而是**让新曲线在原有阈值附近平滑穿过、并在高温段继续加强**。

高温惩罚由**温度**主导、湿度只做小幅加成，这是本轮最重要的方向性修正：原实现把防护只挂在 `hot_humid` 上，等于把"湿"当成了主变量。保留一点湿度项的理由也换了——不是"湿空气锁住香气"（已推翻），而是**热舒适度**：高湿下汗液蒸发散热受阻，佩戴者与周围人本身处在更高的不适阈值，同样浓度更容易越过"过头"线。反过来，干热下蒸发散热有效，皮温往往还**低于**同气温的湿热。

**冷侧两条（取暖加成 / 清冽惩罚）都没有物理支持**——按被引物理算，低温下低挥发材料被压制得更狠，方向甚至相反。保留它们的唯一正当理由是用户偏好与文化预期【文化惯例】，不是挥发学。

**关于 clamp：维持 [0.7, 1.3]，不采纳"收紧到 [0.85, 1.15]"的建议。** 两个理由：① 对抗性复核明确反对收紧——"皮温随气温变化幅度小"只对躯干颈部成立，而手腕是**肢端**部位、受血管舒缩强烈调制，气温 20→30℃ 可能带来 5–8℃ 的皮温差；② 按新曲线算，35℃/90% 得 0.81，若截断到 0.85 就会与 32℃ 的 0.85 重合，**在顶端重新制造塌缩**——正是这次要修的毛病。实际取值范围约 [0.81, 1.12]，clamp 从不触发，是纯安全网。

⚠️ **不要拿 Clausius–Clapeyron 给这些系数背书。** 要标定只能靠用户反馈做 A/B，不能靠再拍一次脑袋、也不能去借一篇文献。

**天气修正的归因必须与数值一起产出**（`scoring.ts:weatherFit` 返回 `{w, tone}`）。此前只返回标量，下游只能靠 `W ≥ 1.08` 反推措辞，于是把冷天给暖调的 ×1.15 也解释成"清爽通透"——2℃ 推烟草香草时会写出「香草·甜调·烟草的调性清爽通透，正合今天的天气」。而这句是 `reasons[0]`，会作为**事实**送进 `/api/explain`，那边的铁律第一条是"只能使用我给你的事实"。数字白名单拦得住编造的数字，拦不住上游喂进去的错误语义。详见 §8。

## 2. 留香与扩散：社区投票 → 档位

### 2.1 为什么不用浓度标签

这是全书**唯一一条在循证复核中被加强而不是削弱**的决定。当初的理由是两条行业常识：

- 浓度决定不了留香，香调结构才是大头。柑橘古龙做成 EDP 依然短命，乌木做成 EDT 依然顽固；
- 浓度与扩散不是单调关系。Extrait 往往比 EDP 更贴肤绵长。

复核后可以说得更硬【实证·中】：**EDC/EDT/EDP/Parfum 的香精百分比区间根本没有任何强制性法规或标准机构定义**，纯粹是各品牌自定的营销惯例——IFRA 自己把 EDT/EDP/Parfum 全部归入同一个 Category 4，从不按浓度区分。也就是说，浓度标签连"可靠的输入"都算不上，它是一个各家定义不同的市场用语。当初凭直觉做的减法，事后看是对的。

因此数据层没有浓度字段（`types.ts:Perfume`）。留香与扩散一律来自社区投票（longevity 1–5、sillage 1–4），浓度标签不参与任何计算。

### 2.2 扩散四档 `scripts/derive.mjs:sillageTier` + `format.ts`

| sillage 均值 | 档 | 档名 | 速览 | 副标签 | 一句话（`DISTANCE_HINT`） |
|---|---|---|---|---|---|
| <1.75 | 1 | 贴身可闻 | 贴肤 | 密闭也安全 | 适合电梯、会议、就医等密闭场合 |
| 1.75–2.5 | 2 | 一臂之内 | 一臂 | 日常安全 | 正常社交距离可感，安全日常 |
| 2.5–3.25 | 3 | 一桌之间 | 一桌 | 注意场合 | 同桌或小房间能闻到，注意场合 |
| ≥3.25 | 4 | 整间屋都是它 | 满室 | 密闭慎用 | 户外、夜场加分，密闭空间慎用 |

没有投票数据时落第 2 档，取中庸。推荐卡、香柜卡、换瓶弹层对同一瓶的叫法统一从这套出。

⚠️ **这四档是产品叙事，不是测量值【文化惯例】。** projection / sillage 在学界没有公认的量化定义或测量协议——连测量装置都是私有专利，数据来源是社区评价者的主观投票。所以档名可以生动，但**解释它的时候必须归因**：详情展开处渲染为「整间屋都是它 · **多数评价者的感受**（户外、夜场加分，密闭空间慎用）」（`format.ts:DISTANCE_ATTRIB`）。紧凑的规格格里保留短档名不加前缀——那里空间不够，而展开处已经把话说清楚了。

### 2.3 留香四段 `format.ts:durationHint` / `durationShort`

| longevity 均值 | 完整话术 | 速览 |
|---|---|---|
| <2 | 散得偏快，出门前喷；下午想起来可以再补一下 | 散得快 |
| 2–3 | 撑得住大半个白天，傍晚有正式场合值得补一次 | 大半个白天 |
| 3–4 | 基本能陪你过完这一天的白天 | 一整个白天 |
| ≥4 | 留得住，晚上多半还在——少喷一点就够 | 可能到夜晚 |
| 无数据 | 留香表现因人而异，用两次你就知道它在你身上能撑多久 | 因人而异 |

**永不给小时数——这条红线现在有了真正的科学依据【实证·中】**，而不只是产品洁癖：同一款香在不同个体皮肤上的蒸发量差异达到统计显著水平，是留香预测中最大的单一不确定性来源。皮肤水合度、皮脂、表面粗糙度、体温调节都在起作用，而这些我们一个都不知道。任何"留香 X 小时"都是把一个我们没测量、也无法测量的量说成已知。

顺带说，行业侧也没有可借的数据：EDC/EDT/EDP/Parfum 的香精百分比**没有任何强制性法规或标准机构定义**，纯粹是各品牌自定的营销惯例（IFRA 自己把 EDT/EDP/Parfum 全部归入同一个 Category 4，从不按浓度区分）。留香时长由配方中各分子的蒸气压/分子量分布决定，与总浓度不是单调关系——一支 20% 浓度但主体是柑橘萜烯的 Extrait，完全可能比 8% 的木质麝香 EDT 更早消失。这正是 §2.1「为什么不用浓度标签」的补充依据。

**2026-07 重写**：原话术里的「约半天」被判定为仍然偏精确——那个「约」字暗示背后有过一次测量。现改为纯定性描述 + 一个可执行动作（要不要补、什么时候补），让这句话的信息量落在"你该怎么办"上，而不是落在一个假装知道的数字上。另有一条联动：场景解析出的在场时长落在 ≥6 小时档，而这瓶又撑不到一整个白天（longevity <3）时，话术会追加「在外时间不短，带上分装中途补 1 下更稳」（`usage.ts:computeUsage`）。

### 2.4 低票与手动记录：不确定性外显

- 扩展集低票记录（国货白名单等）带 `lowVotes` 标记，解释文案明说「这瓶的社区数据还少，判断偏保守，你的反馈会让它更准」（`usage.ts:buildReasons`）；
- 手动建卡（`custom`）没有社区数据，按所选香调的典型情况估计，留香话术自动落「因人而异」（`types.ts` + `format.ts`）。

**修复：构建管线曾把「没有票」当成「0 分」。**

源数据的量表是 rating/longevity/priceValue **1..5**、sillage **1..4**（`ledecanteur/SCHEMA.md`），**0 在任何一个量表上都超出下界**——它是"这一项没有票"的哨兵值。但管线写的是 `d?.longevity?.average ?? null`，而 `??` 只兜 `null`/`undefined`，**`0` 会原样通过**。

实测代价（扩展集 35,990 条）：`longevity===0` **458 条**、`sillage===0` **444 条**、`rating===0` **252 条**，且高度集中在**国货**（七寸九、RE调香室、馥刻、闻献、银杉…），多为 1–2 票。下游后果是纯编造：

- `durationHint(0)` → 「散得偏快，出门前喷…」——我们对它的留香一无所知；
- `sillageTier(0)` → 1 档「贴身可闻 · **密闭也安全**」——**这还是一句安全相关的断言**。

讽刺的是：仓库特意做了国货白名单以求包容，却基于零数据替这些国货编造了留香与扩散。

修法是把守卫下沉到共享的 `derive.mjs:voteAvg`（低于量表下界一律判 null），`build-ext.mjs` 与 `extract-terms.mjs` 共用。重建后 0 值归零、**记录数不变（35,990，没有丢数据）**，`sillageTier` 回落到 2 档中庸，留香话术接回「因人而异」。单测「构建产物里不得出现 0 分」对主目录 + 全部 64 个分片做全量校验。

这与 §6.1 的「平坦分布 = 满分」是**同一个认知错误的不同形态**：**"没数据"被当成了一个值。** 加数据源时先问一句：这个字段的"缺失"长什么样？

## 3. 喷量与位置

### 3.1 喷量基础档 `usage.ts:computeUsage`

扩散越强，喷越少：

| sillage 均值 | 基础档 |
|---|---|
| ≥3.2 | 1–2 下 |
| 2.4–3.2 | 2–3 下 |
| <2.4 | 3–4 下 |

缺数据时按 2.5 处理，落在 2–3 下。喷量切点（2.4 / 3.2）与扩散四档的命名切点（2.5 / 3.25）是两套独立常数，方向一致。

### 3.2 修正叠加 `usage.ts:computeUsage`

修正按档位递推，在区间上加减 1，不做加权求和：

| 修正 | 条件 | 动作 |
|---|---|---|
| 密闭 / 人挤 | 场合密度为 dense（通勤）或 closed（上班、正式场合），见 §4.1 | 上下限各 −1 |
| 寒凉 × 清淡 | 体感寒凉且 sillage <2.4 | 上限 +1 |
| **高温 × 强扩散** | 体感**闷热潮湿或干热**且 sillage ≥3.2 | 上限 −1。此前只挂在闷热潮湿上，是把"湿"当主变量；主变量是温度，干热同样让香水爆得更快 |
| 餐桌 | meal 开关命中（§5.2） | 上限 −1 |
| 「用力过猛」组合 | 见 §4.4 | 直接压到 1 下 |
| 想贴身 | 场景解析 intimacy = close | 上限 −1 |
| 想被注意到 | intimacy = broadcast | 上限 +1 |
| 明说别太冲 | avoid 含 too_strong | 上下限各 −1 |
| 个人校准·嫌冲 | perceivedStrength ≥0.4 | 上限 −1；≥0.7 时下限再 −1 |
| 个人校准·嫌淡 | perceivedStrength ≤−0.4 | 上限 +1 |

任何修正路径之后强制 1 ≤ lo ≤ hi ≤ 5，不会出现「2–1 下」这类反向区间。输出话术固定为「N 下」或「lo–hi 下」。

### 3.3 成功配置复用 `usage.ts` + `recommend.ts:aggregateBias`

同一温度档、同一场合下，你曾对这瓶反馈过「刚好」，引擎就复用那次的量（取当时建议区间的中值），并显式说明：「上次同样天气、同样场合你说『刚好』——就按那次的量来。」成功配置同键只留最新一条，每瓶至多 5 条。校准必须被感知，见 §7.6。

**但它只能在安全上限之内复用。** 原实现把这一步放在全部安全阀**之后**无条件覆盖，于是「用力过猛」组合本已压到 1 下的结论，会被一条"上次 4 下刚好"直接顶回 4 下。现在的做法是：先让通用规则算出这个场合 × 这个天气 × 这瓶香的**安全上限**，成功配置在这个上限内取值；被压低时话术改成「不过今天这个场合更收着些，先按更少的量来」——**被压低这件事必须说出来，不能默默改数**。

个性化不能凌驾于安全阀之上：上次「刚好」记的是上次的场合，覆盖不了今天更封闭的会议室、更闷的天。

### 3.4 位置策略 `usage.ts:computeUsage`

| 情境 | 位置 |
|---|---|
| 想贴身（close） | 手腕、颈侧贴身 |
| 密闭场合（通勤 / 上班 / 正式） | 手腕、衣物内侧 |
| 约会 | 颈侧、手腕、发梢少量 |
| 聚会 | 颈侧、胸口 |
| 其余 | 手腕、颈侧 |

**【已推翻】「脉搏点」理论。** 原手册用"脉搏加出汗区、血流丰富所以促进挥发"来解释部位选择。这个说法流传极广，但**找不到任何同行评议依据**，而且实测的人体分区皮温恰恰不支持它：

| 部位 | 实测皮温 | 与民间说法的关系 |
|---|---|---|
| 颈前 | 约 35℃ | 全身最热区域之一 ✓ |
| 前臂 | 约 33℃ | **明显更低** ✗ |
| 耳部 | 约 30℃ | "经典脉搏点"里**最冷**的区域之一 ✗ |

⚠️ **使用这批数据的三条限制**（不写清楚就会重蹈"拿论文背书"的覆辙）：

1. 该实测是**单一室温条件**（约 24℃、静息）下的横截面测量，**从未操纵过气温**。它能说明"部位之间有差异"，不能说明"气温变化时各部位怎么变"；
2. **手腕从未被单独测量**。常被引用的 32.6℃ 是**前臂**读数，两者不是一回事——本手册上一版就犯了这个错；
3. 手腕是**肢端**部位，受交感性血管舒缩强烈调制，个体间腕温差可达 2.9℃——它是全身**最不可预测**的落点。任何基于手腕皮温的精细推理都不该做。

正因如此，注释与文案里**都不写带小数的皮温值**：两次独立核查对颈部给出的读数就不一致（35.0±0.5 vs 34.7±0.6）。一个连复核者之间都对不齐的数字，不配印在产品里。

**但"皮温差改变挥发速率"本身是成立的物理【实证·中】**，所以部位真正的意义是一个**投射档位盘**：

```
颈侧（最热，投射最强） ＞ 手腕（居中） ＞ 耳后 / 衣物内侧（最凉，释放最慢）
```

这比"少喷一下"更精细——**不牺牲你自己闻到的体验，只收敛别人闻到的强度**。这也是原引擎里完全缺失的一个自由度。

两条覆盖规则：

- **高温改写**（闷热潮湿**或干热**，此前只有闷热潮湿）：手腕改到衣物内侧，颈侧改到耳后或衣领内侧，胸口改到衣物内侧，发梢剔除。方向是"往凉的一端挪"——顺带说明，织物之所以更慢，不只是温度低于皮肤，还因为它是**惰性多孔基质**，而皮肤会吸收并与皮脂相互作用【实证·中】。
- **「用力过猛」组合**：位置整体放低到腰侧、衣物下摆内侧【行业惯例】。

**关于发梢**：毛发确实是比皮肤更好的香气载体，但它位于呼吸带高度、随头部运动持续搅动空气、比表面积又大，是**投射最不可控**的落点。所以做了两处收紧：

- 原来约会场景**无条件**追加"发梢少量"，现改为**只在 `sillage < 2.8` 且非高温时**才给；
- 措辞从"发梢少量"改成**「喷一下梳子，再梳过发尾」**——「少量」是用户无法执行的指令（少量是多少？），喷梳子是同等效果、几乎零风险的替代。

高温时整条剔除，理由是出汗与投射失控，**不是"酒精伤发"**——后者是没有依据的美妆口头禅【实证·弱】。

**关于喷衣物**：最终建议里只要出现"衣物"，就无条件追加一句织物提示——高浓度乙醇 + 香精油脂 + 有色浸膏的光氧化黄变，对真丝、醋酸纤维和浅色外层是实打实的留印风险【行业惯例】。特别注意「用力过猛」组合强制改成的「腰侧 + 衣物下摆内侧」恰好最容易接触外层衣物，更需要这条。

这条提示的价值在于：它是一个**真实且可辩护的实用风险**，比编造的安全风险有价值得多。同理，"喷衣物比喷皮肤留香久"可以作为建议保留，但**理由必须写成"减少皮肤直接接触"**（香料是最常见接触致敏原之一，有 SCCS 依据），**不要承诺更长留香**——那一条只有行业观察，没有对照实验。

**关于"喷完不要摩擦手腕"**：这条流行建议的**结论**可以留，**解释必须改**。"摩擦会破坏/打碎香料分子"是明确错误的——摩擦力在物理上无法断裂共价键。真实机制是摩擦生热加速前调挥发，以及把香液铺开、压入皮肤纹理从而增大蒸发面积【实证·中】。

**关于柑橘光毒性**：复核中一度出现"高温日晒 + 柑橘 → Berloque 皮炎"的硬规则提案，最终**未采纳**。临床风险真实存在且有标准机构背书，但 IFRA 已把日晒部位成品中的佛手柑内酯限到 15 ppm，合规零售香水的实际风险有限，**不应做成硬阻断**。顺带可以主动打脸一个流行谬误：「夏天别喷柑橘香会变黑」对 IFRA 合规成品基本不成立【实证·弱】。

**有效社交距离**：推荐卡上展示的距离档取「喷后有效档」而非原始扩散档。已生效的减档——密闭、贴身、明说嫌冲、个人校准嫌冲——每项降 1 档，封顶降 2 档，避免同屏出现「喷 1 下」却仍标「整间屋都是它」的自相矛盾（`usage.ts` 中 effTier 的计算）。

空间密度进两处：喷量修正（§3.2）与密闭三道闸（§5.1）。

### 4.2 场合从哪来：场景理解 `src/app/api/parse-intent/route.ts`

用户可以点场合，也可以说一句话（「去前任婚礼」「第一次见投资人」）。一句话则经 DeepSeek 解析、zod 校验，产出结构化补丁：场合、正式度（0–1）、亲密距离（close / neutral / broadcast）、规避项（别太甜 / 别太冲 / 别太端着 / 别腻 / 别太随意）、关系张力、餐桌开关、受控的一句话社交风险、≤12 字的人话摘要。三条设计约束：

- 在场时长只许 2 / 4 / 6 / 9 档位值，杜绝「7.5 小时」式的伪精确；
- 解析失败时降级为关键词启发式，永远给出可用的结构；婚礼、面试会落到正式场合，并自动挂上「别太冲」；
- LLM 的场景常识只能走受控字段 riskNote（≤40 字），不进正文（§8.4）。

规避项兑现在打分侧（`scoring.ts:avoidPenalty`）：命中别太甜或别腻，甜系主调 ≥50 的一律乘 0.68；命中别太冲，满室档乘 0.6、一桌档乘 0.8；命中别太端着，带「正式商务」风格标签的乘 0.8；命中别太随意，「日常百搭 / 清新通勤」乘 0.85。

### 4.3 场合适配的方向表 `scoring.ts:occasionFit` + `occasion-priors.ts`

> ⚠️ **本节全部是【文化惯例】，不是科学。** 循证复核的结论很直接：「职场偏清爽木质、约会偏甜花、运动要清新」这类命题**检索不到任何同行评议的消费者研究**，而且强烈依赖地域（中东市场对沉香在正式场合的接受度与东亚完全不同，中国职场规范更是零数据）。
>
> 保留它是对的——用户打开氛寸要的正是"一个懂行的人会怎么选"，删掉产品就没有判断了。但有两条纪律：**① 不许对用户宣称它有科学依据**（文案只说"这类场合一般更稳妥"，绝不说"研究表明"）；**② 不许为了"更精确"去微调这些系数**。
>
> 为了让这件事在**结构上**看得见而不只是靠一段注释，全部风格权重已抽到独立文件 **`src/lib/occasion-priors.ts`**，并统一降到**一位小数**——两位小数会让人误以为它们被标定过。0.4 就是"挺重要"，0.2 就是"有点影响"，仅此而已。
>
> 注意区分留在引擎里的**安全项**（A 类）：「强扩散香在封闭场合扣分」「密闭场合减喷量」有扎实的公共卫生依据（约 1/3 人群报告对香味制品不良反应，CDC / CCOHS / CDPH / 美国肺脏协会均有正式无香政策），它们理直气壮，不要跟风格先验混为一谈。

引擎不用族群与场景交叉展开的巨型矩阵，而是用六个香调组，配上每场合一组加减方向，基准 0.5。组成员均为**数据集实有键**（幽灵键已清除，见 §1.3）：

| 组 | 成员 accords |
|---|---|
| 清爽 | citrus, aquatic, marine, green, aromatic, fresh, ozonic, herbal, mineral |
| 甜感 | sweet, vanilla, caramel, honey, chocolate, gourmand |
| 琥珀木质 | amber, woody, oud, balsamic, patchouli |
| 花香 | floral, white floral, yellow floral, rose, tuberose, violet, iris, lactonic |
| 泥土暗调 | earthy, leather, tobacco, smoky, animalic, patchouli |
| 辛香 | warm spicy, spicy, fresh spicy, cinnamon, soft spicy |

每组取成员中的最强 accord 强度（0–100 归一后）参与：

| 场合 | 加分 | 减分 |
|---|---|---|
| 约会 / 聚会 | 甜或花取大 +0.4；温和琥珀木质 +0.1（强度 60 以上斜坡淡出，连续函数不设悬崖） | 泥土暗调与半权辛香（×0.5 折算）取大 −0.3；纯清冽（清爽 >70 且不甜不花）−0.2，安全但不够暧昧；约会且满室档 −0.2 |
| 正式 / 上班 / 通勤 | 干净木质（×0.8 折算）/ 清爽 / 辛香（×0.6 折算）取大 +0.3 | 甜 −0.4；花 −0.2；泥土暗调 −0.2；满室档 −0.2 |
| 运动 | 清爽 +0.4 | 甜 / 琥珀木质 / 泥土暗调取大 −0.5；一桌档以上 −0.1 |
| 居家 / 休闲 | 柔和皆可：甜、木、清爽、花取大后 ×0.6 折算 +0.2 | 满室档 −0.2 |

（这些数与旧版的 0.42 / 0.22 / 0.18 / 0.12 差异都在四舍五入范围内，全部 56 条单测未受影响——正说明它们本来就没有精确到那一位的必要。）

**软下限**：结果低于 0.05 时，引擎不把它硬夹到常数，而是单调压缩进 (0, 0.05]，保住候选之间的相对次序。若不这样做，同质香柜的多瓶会一起撞到底板；场合项权重 0.43、各项里最高，在这种场景下却退化为同分，区分力归零。方向是【行业惯例】，系数无实证标定，验证方式见附表。

### 4.4 「用力过猛」组合 `usage.ts:overdressedCombo`

国内语境下最容易被负面评价的搭配，三个条件同时命中：

> （sweet 或 vanilla ≥50，或 white floral ≥50）×（扩散 ≥ 一桌档）×（通勤 / 上班 / 正式场合）

触发后三连：喷量直接压到 1 下、位置放低到腰侧 / 衣物下摆内侧、附风险文案「甜和扩散都偏高，这类场合容易显得用力过猛——压到 1 下、放低位置会体面很多。」这条针对「柜姐感」联想【文化惯例】：办公室里的浓甜白花，在国内的解读往往不是「讲究」而是「过了」。

## 5. 气味礼仪与中国语境

### 5.1 密闭空间三道闸

**这是全套规则里依据最硬的一条【实证·中】**，而且依据不是"礼仪"，是公共卫生：约三分之一人群报告对香味制品有不良反应，且有可量化的职场成本；CDC、加州公共卫生部、CCOHS 等机构有正式的无香政策，医院与部分办公场所强制执行。

请注意它的正确论证方式：**不要用"密闭空间气味累积"这类空气动力学说法**——那会在"密闭但空无一人的房间"里给出明显错误的建议。真正的理由是**对共处空间里其他人的克制**，所以它取决于有没有人，而不是取决于换气率。

#### 5.1.0 无香场合：唯一一条建议「不用」的规则

`Context.fragranceFree` 命中（就医 / 探病 / 陪诊 / 体检 / 病房 / 产检）时，引擎直接返回：

```
喷量 [0,0]「今天不用」 · 部位 [] · 裁决 avoid · 不调 LLM · 不给备选 · 不问「刚好吗」
```

**为什么它排在最前面**：这是全引擎依据最好的一条规则，而此前完全不存在——更尴尬的是 `format.ts:DISTANCE_HINT[1]` 早就写着「适合电梯、会议、**就医**等密闭场合」，却没有任何规则兑现"就医"这两个字。这正是本轮反复出现的那类缺陷：**文案承诺了引擎没做的事**。

实现上有四条纪律：

1. **放在 `computeUsage` 的最前面**，先于一切规则返回。任何个人偏好、成功配置、场合加成都不该把它覆盖掉——单测里用 `likeScore=1 + successConfigs=[4 下]` 的极端偏置验证它顶不动。
2. **不交给 LLM**（`hooks.ts:useExplain` 提前返回）。SYSTEM 对 `avoid` 的铁律要求"话锋一转，给一句『但你今天要是就想用它，可以这样把影响降到最低』"——那套措辞对约会、通勤是对的，**对病房是错的**。这里没有"降到最低"的版本，只有"别用"。
3. **UI 整块换掉**（`RecommendationCard`）：不再显示喷量／社交距离／留香三格与"喷在哪"。答案是"今天不用"，下面却挂着"社交距离：贴身可闻"，和「今天不建议」下面挂着「喷 2 下」是同一种自相矛盾。
4. **启发式必须兜住**（`parse-intent:heuristic`）。这条规则的价值恰恰在 DeepSeek 不可用时也不能失效，所以关键词表（医院/看病/就医/门诊/诊所/探病/住院/病房/体检/陪诊/化疗/产检/月子）与 LLM 提示词双路并行。

文案分工：`risks[0]` 说**为什么**（进解读位），`usage.note` 说**那怎么办**（进分寸位）。两处必须互补，不能是同一句话的两种说法。

#### 5.1.1 密闭空间三道闸

强扩散撞上密闭空间——同一个事实，在引擎里要过三道互相独立的闸：

1. **喷量闸**：dense / closed 场合上下限各 −1（`usage.ts:computeUsage`）；
2. **风险闸**：满室档遇上密闭场合，给出风险文案「空间偏封闭、人也多，这瓶气场较大——建议只喷 1 下，或换一瓶更贴肤的。」（`usage.ts:computeRisks`）；
3. **裁决闸**：满室档遇上通勤 / 上班 / 正式场合，直接判 avoid——「今天不建议」（`recommend.ts:computeVerdict`）。

风险文案的句式是刻意的：后果描述加出路，不用「千万别」。

### 5.2 餐桌规则 `types.ts:Context.meal` + `usage.ts`

气味干扰味觉是餐饮共识，高端餐饮甚至明示谢绝浓香【行业惯例】——顺带说，"气味影响味觉感知"本身有跨模态知觉研究支持，但"餐厅谢绝浓香"是行业惯例，不是从那些研究推出来的。meal 开关由场景理解给出（婚宴 / 日料 / 火锅 / 酒局都算），命中后：

- 喷量上限 −1（`computeUsage`）；
- 这瓶偏甜重或树脂偏厚（甜家族 / 树脂琥珀家族最强 ≥55，两者分开算，见 §5.4），或扩散在一桌档及以上，则追加风险文案「这顿饭是场合的一部分——它的存在感会和食物气味打架，喷得比平时更收着些。」（`computeRisks`）

### 5.3 中国语境的本土化差异【文化惯例】

1. **整体容忍度低一档**：国内公共场合对明显香水味的默认反应偏负面，「好大味儿」就是一句负面评价。这条不对应某一行代码，而是解释了一批参数的取向：正式 / 上班 / 通勤对甜与花的重罚（−0.42 / −0.22），以及满室档在密闭场合直接判 avoid。
2. **「柜姐感」联想**：即 §4.4 的「用力过猛」组合，专项处理。
3. **回南天 / 梅雨**：原本并入闷湿体感，**已删除**（§1.2）。换上的是有依据的那一半——回潮天真正与香水相关的是衣物霉潮本底气味，只驱动一句文案。这仍然是照抄欧美温标做不出的判断，只是这一次它是对的。
4. **「若有若无的好闻」是国内最高频正面评价**：产品默认审美是宁淡勿浓，体现在打分取向与 avoid 裁决上。

⚠️ 本节整体是【文化惯例】而非实证。循证复核明确指出：「东亚消费者偏好更淡」这类论断找不到可引用的消费者研究。保留它是对的——本地化判断正是产品价值——但**不许对用户宣称它有研究支持**。

### 5.4 甜 ≠ 琥珀：拆桶及其代价

原实现用 `max(sweet, amber, vanilla) ≥ 55` 作为"偏甜重、久了发腻"的判据。这是**香水学上的分类错误**：琥珀属树脂香膏家族（劳丹脂、安息香、苏合香），而现代由 Ambroxan / Cetalox 骨架主导的"琥珀"是干燥、矿物、近乎无甜的。

在本仓库真实数据上的代价可以精确点数：**主目录 112 款**命中"amber ≥55 但 sweet/vanilla <30"，包括 —— 蔚蓝浓香精（amber=86, sweet=0, vanilla=0）、旷野、当蓝、红色香水540、探索家、**绿爱尔兰花呢**（著名的干绿木质）。它们全都会被告知「它偏甜重，上身久了容易发腻」。这是整份缺陷清单里**最容易被当场证伪**的一句：打开线上版输"上海 + 蔚蓝"就能复现，一句"蔚蓝哪里甜？"人设就穿了。

（同文件的 `overdressedCombo` 一直只取 sweet/vanilla，是对的——说明这里本就是疏漏，不是设计。）

现在的处理（`scoring.ts:sweetness` / `balsamicWeight`）：

| 桶 | 成员 | 触发的风险文案 |
|---|---|---|
| 甜 / 美食调 | sweet、vanilla、caramel、honey、chocolate、cacao、coffee、almond、coconut、gourmand | 「甜感偏重，上身久了容易发腻」 |
| 树脂琥珀 | amber、balsamic、oud、beeswax | 「树脂琥珀感偏厚，高温里存在感会比你以为的更强」 |

`avoidPenalty` 的 `too_sweet` 也同步只取甜桶——此前用户说一句"别太甜"，会把 sweet=0 的蔚蓝罚掉 32%。

**三条必须写下来的限制**【行业惯例】：

1. **不要说干琥珀"完全不甜"。** 反向证据很硬：供应商侧对 ambroxan 的描述就包含 "sweet"、"labdanum"、"dry, woody"；ambergris 本身常被描述为 "marine, animalic and sweet"。准确的说法是：干琥珀的甜是**矿物木质框架上的微甜，不产生美食调那种累积性的腻**——是「不 cloying」，不是「不 sweet」。工程上这刚好够用，因为要预测的是"久了发腻"而不是"甜不甜"。
2. **数据层根本无法区分干琥珀与甜琥珀。** Fragrantica 的 accord 词表里没有 ambergris / ambroxan，Ambroxan 主导的香只能落到 amber(+woody)，与经典甜东方琥珀共用同一个标签。所以只能做「amber 一律不计入甜桶」这种粗粒度处理，做不到精细判别。
3. **拆桶有明确代价，不装作没有。** 像 Shalimar、Ambre Nuit 这类甜味主要由 amber accord 承载、而 sweet 标签可能 <55 的经典东方香，会**漏报**发腻风险。这是刻意接受的偏向：宁可漏报，也不要对 112 款一点不甜的香误报。

## 6. 季节与时段投票的使用

### 6.1 平滑与相对主场归一

**先给这份数据定性【实证·弱】。** Fragrantica 的季节投票**不是"季节适不适合"的物理度量**，而是**群体使用惯例的众包统计**。它有真实但间接的机制支撑（温度确实改变挥发与感知），也混入了大量与物理无关的文化联想；此外还有系统性偏差：用户构成、投票动机、北半球偏斜、对华南气候的错配。

结论：**只能当先验，不能当主判据**。这也是为什么季节只占 0.38 权重、而且必须能被个人反馈压过（§7）。顺带说，「清爽调适合夏天、暖调适合冬天」本身也找不到任何同行评议的消费者研究——「暖调让人觉得更暖」有跨模态知觉证据，但那是**感知效应不是化学效应**：香草不会让香更持久。

- **拉普拉斯平滑**：季节占比在数据构建期做平滑（ALPHA = 5），防的是低票噪声（`scripts/derive.mjs:seasonPct`）。
- **相对主场归一**：季节适配分 = 当前季占比 ÷ 该瓶最高季占比，主场得 1（`scoring.ts:seasonFit`）。这里不用「占比 >0.35 算夏香」式的绝对阈值，因为投票行为有系统性偏置，四季分布偏平的瓶子会被绝对阈值一刀切没。时段适配同构（`daypartFit`）。
- **置信度收缩：「不知道」不等于「满分」。** 相对主场归一有一个致命性质——**分布越平坦，得分越高**。手动记录的香 `seasonPct` 是我们诚实填的 0.25×4，代入后四季恒得 **1.0**：一瓶我们一无所知的香，在季节项上打平一瓶两万票认证的完美对季香。低票扩展集同理，三五票的噪声分布偶然出现尖峰就被当成强信号。

  修法是按票数向**全库经验均值**收缩：

  ```
  置信度 conf = people / (people + 60)      // 手动记录恒为 0
  收缩后     = 锚点 + (原始值 − 锚点) × conf
  锚点：seasonFit 0.671、daypartFit 0.771   // 在 1500 款主目录上实测，不是拍的
  ```

  主目录最低票数 1131 → conf ≥ 0.95，几乎不受影响；手动记录落到全库平均水平，而不是落到满分，也不是落到最差——**"不知道"就该待在平均那一格**。

  配套的表达纪律：**凡是"关于社区数据的断言"，都要过同一道票数门槛** `conf ≥ 0.75 且非 custom/lowVotes`。目前有两处：

  - `buildReasons` 的「正是它的主场季——社区投票里它更偏◯季」
  - `computeRisks` 的「大家更多在◯季用它，今天用会有点反季」

  后者曾经**漏掉了这道门槛**。手动记录的香因 `seasonPct` 恒为 0.25×4、差值恒 0 而侥幸不触发；但低票扩展集（三五票的噪声分布）会触发，于是拿三票去对用户说"大家更多在冬季用它"。这与前者是同一类编造，只是藏在风险文案里、晚一步才被发现——**加规则时要连同它的所有出口一起加**。

### 6.2 温度盖过月份 `season.ts:seasonFromDateTemp`

月份定基准季节，但 ≥28℃ 一律按夏、≤6℃ 一律按冬。Fragrantica 投票者以欧美温带用户为主，他们的「夏天」不是广州的夏天，本地实时气温比日历更接近体感真相。急性天气另有乘性修正兜底（§1.3），两层各司其职。

### 6.3 反季的两道门槛

主场季与当前季不一致时，按占比的**相对差**分两级：

- 相对差 ≥0.12 时，给出风险提示「大家更多在 X 季用它，今天用会有点反季。」（`usage.ts:computeRisks`）
- 相对差 ≥0.22 时，直接进 avoid 裁决（`recommend.ts:computeVerdict`）

用相对差而非绝对阈值，理由同 §6.1。

### 6.4 权重结构 `scoring.ts:score`

> 总分 = (0.38 × 季节 + 0.19 × 时段 + 0.43 × 场合) × 天气 W × 质量先验 Q × 个人偏好乘子 × 场合差评乘子 × 场景规避乘子

- **场合权重高于季节**：「今天去哪儿」比「现在什么季」更该决定喷哪瓶。急性温度已由 W 兜底，让场景赢下真正的平局。
- **质量先验 Q**：社区评分做贝叶斯收缩（C = 30，靶心 M = 4.0）后压进 [0.96, 1.04]。「今天喷哪瓶」由情境决定，社区评分只当轻微 tiebreak，不允许高分香跨场景通吃；未评分记 1.0，不惩罚。收缩靶心与中性锚点取同一个值，否则「中评加少票」会比「没评分」更差。
- 个人偏好与场合差评乘子见 §7.4。

## 7. 用后反馈的校准规则

### 7.1 一问四答 `FeedbackBar.tsx`

只问「今天，刚好吗」一句，四个选项：淡了点 / 刚好 / 太冲了 / 不合场合，点一下即完成。每瓶每天最多记一次（当日去重，刷新不重复计入）。答完只说一句确认，不追问。反馈即视作当天穿过，这瓶当天落进香历。

### 7.2 环境归因 `FeedbackBar.tsx:envEatsLongevity` + `recommend.ts:aggregateBias`

「淡了点」是所有反馈里**最容易被误读**的一条。它有两条独立的归因路径，命中任一路径都不进个人喷量校准——既不让香水背锅，也不让校准被污染。反馈快照里存了体感与湿度（`types.ts:Feedback.context`），归因可回溯。

**① 嗅觉适应归因 `adaptation_attributed`【实证·中，本节依据最硬的一条】**

判据：这瓶在最近 3 天里被记录穿过 ≥2 次（`FeedbackBar.tsx:recentlyRepeated`）。

依据：嗅觉适应是**双通路的真实生理现象**——外周/皮层通路数十秒起效，嗅球通路数分钟起效并可持续 30 分钟以上。更关键的是：**重复暴露于同一款气味，会造成持续数周的、气味特异性的敏感度下降。**

这意味着原实现存在一个**会主动放大自身错误的正反馈回路**：

```
你闻不到 → 系统判定"喷少了" → 建议多喷 → 适应更深 → 还是闻不到 → 再多喷
                                              ↑
                        而这期间，周围人闻到的浓度一路上升
```

引擎里其他所有缺陷都是"算错了"，只有这一条是"越用越错"。所以它必须被掐断。

确认语也正是氛寸最值得说出口的一句洞察：

> 「这几天你连着用了它——最先「失灵」的多半是鼻子，不是香水。你闻不到，旁边的人未必。这笔先不加喷量；明天换一瓶，隔两天再回来闻它。」

注意它同时给了出路（换一瓶、隔两天），而不是单纯否定用户的感受。

⚠️ **不许量化。** "有多大概率其实是适应"这个数字**没有任何文献可以支撑**，不能编，也不能写进文案。我们只知道这个混杂因素真实存在且强度可观，不知道它占多少。

**② 环境归因 `env_attributed`【实证·弱】**

判据：闷热潮湿 / 干热体感，或 ≥28℃。确认语：「记下了——不过今天这天气本来就吃留香，这笔算天气的，不扣它的分。」

两者同时命中时，**嗅觉适应优先**——它的证据更硬，也更有价值。

### 7.3 聚合、衰减与钳位 `recommend.ts:aggregateBias`

| 反馈 | 偏好 likeScore | 体感强度 perceivedStrength | 其他 |
|---|---|---|---|
| 刚好 | +0.3 | — | 沉淀成功配置（场合 × 温度档 → 当时喷量中值），同键留最新，至多 5 条 |
| 太冲了 | −0.1 | +0.4 | — |
| 淡了点（未归因环境） | −0.05 | −0.4 | — |
| 不合场合 | −0.15 | — | 该场合错配计数 +1 |

所有权重每月乘 0.9 衰减，三个月前的反馈约剩七成话语权。口味会变，偏置不能只增不减，正负双向天然抵消。两项均钳位在 [−1, +1]，防止连点把系统带飞。

### 7.4 校准的兑现路径

每个信号都有明确的生效位置：

| 信号 | 生效处 | 幅度 |
|---|---|---|
| likeScore | 总分乘子 | 0.75–1.25（`scoring.ts:score`） |
| perceivedStrength | 喷量与有效距离 | ≥0.4 上限 −1（≥0.7 下限再 −1）、有效社交距离降 1 档；≤−0.4 上限 +1（`usage.ts`） |
| sceneMismatch | 该场合总分 | 每次 −10%、封顶 −30%，别的场合不受牵连（`scoring.ts`） |
| successConfigs | 喷量 | 同情境直接复用并显式说明（§3.3） |

### 7.5 轮换与隐式差评 `recommend.ts`

- **轮换新鲜度** F(d) = 1 − 0.6 × 0.5^(d/2)，d 为距上次采纳隔了几个本地日。d=0 时取 1，当天答案不摇摆；往后 d=1 约 0.58、d=2 为 0.70、d=4 为 0.85、d=7 约 0.95。昨天刚喷的自然让位，久置的自然浮起。新鲜度只影响排序，不改内容分与裁决：「这瓶适不适合今天」和「要不要连着喷它」是两个问题。
- **换瓶隐式差评**：主推被手动换掉，是「分数说它行，你说它不行」。一瓶在 7 天窗口内、至少 2 个不同天被换掉，排名乘 0.8；这个惩罚随时间自动失效，不永久拉黑（`swapPenalty`）。
- **同分轮换**：排名差 <0.012 视作同分簇，簇内按 hash(瓶 id, 本地日) 稳定轮换。次序上先严格降序、再簇内轮换，epsilon 不进排序比较器——epsilon 比较器不满足严格弱序，同质香柜下会出现分高者排后。日切以本地日为准，避免「今日之选」在早上 8 点整突变。

### 7.6 铁律：校准必须被感知

每次校准生效都显式说出来：成功配置复用的说明进「为什么」要点第一条（`recommend.ts:buildPick`），反馈回执直接预告下次的动作（「记下了，下次默认帮你少喷半下。」）。

## 8. 表达规范：如何说人话

完整的术语表、话术红线与文案范例见《[声音与文案](声音与文案.md)》，本节只认领与规则相关的四条。

### 8.1 总原则

1. **一律体感锚点，禁裸数字**：留香说「大半个白天」，距离说「一臂之内」，喷量说「2–3 下」（`format.ts` / `usage.ts`）。
2. **每条建议带「为什么」**：规则生成的要点可追溯到本手册，同时是 DeepSeek 不可用时的兜底解释（`usage.ts:buildReasons`）。解释永远不依赖 LLM 在线。
3. **不确定性外显**：低票记录明说「判断偏保守」，手动记录明说「按所选香调的典型情况估计」（§2.4）。

### 8.2 数字白名单 `numguard.ts`

反伪精确靠代码：允许出现在 LLM 输出里的数字，仅限我们递给它的事实字符串里出现过的数字。事实之外的任何数字（「留香 6.2 小时」「3.7ml」）都视为编造，整段退回确定性模板。

### 8.3 裁决三档 `recommend.ts:computeVerdict`

每个候选给一个用香裁决：good 推荐 / caution 留意 / avoid 今天不建议。avoid 的三条触发：天气修正 ≤0.82、反季相对差 ≥0.22、满室档遇上密闭场合。caution：有任何风险条目，或天气修正 <0.95。裁决不迁就用户，确实不合的场景明确判 avoid，但话锋一转给退路：「你要是今天就想用它，就……把存在感压到最低」。这段退路话术来自 `src/app/api/explain/route.ts` 的确定性模板；LLM 回复若不含否定语义，代码会强制回退到该模板。

### 8.4 受控风险通道 `parse-intent`

LLM 对场景的社交常识（「婚礼焦点是新人，不宜喧宾夺主」）只能以 riskNote 这一个受控字段（≤40 字、zod 校验）进入风险提示，去重后追加，不允许自由发挥进正文。规则引擎决策，LLM 表达。

## 附：置信度总览与验证方式

验证全部走反馈数据结构（`types.ts:Feedback`）：每条反馈带完整情境快照（季节、时段、温度、场合、体感、湿度）、当时的建议喷量与归因标签，够做分桶回归。

| 模块 | 复核后证据等级 | 上线后验证方式 |
|---|---|---|
| §1 环境物理 | 方向【实证·弱】，**全部系数无实证标定** | 「太冲了 / 淡了点」按 `context.feel` × 温度档分桶，回归 weatherMultiplier 的系数方向 |
| §2 档位映射 | 「不用浓度标签」【实证·中】；档位切点【行业惯例】 | 未归因的「淡了点」聚在哪个留香档，检验 durationHint 切点 |
| §3 喷量与位置 | 密闭减量【实证·中】；部位=投射盘【实证·中】；喷数档【行业惯例】；**脉搏点【已推翻】** | `Feedback.sprays` 快照 × rating，「刚好」的喷量分布对基础档回归 |
| §4 场合适配 | 强扩散扣分【实证·中】；**按香调家族的加减分全部【文化惯例】**，已隔离到 `occasion-priors.ts` | scene_mismatch 按 `context.occasion` × 主香调组聚合 |
| §5 礼仪与中国语境 | 无香政策【实证·中】；甜/琥珀拆桶【行业惯例】；本土差异【文化惯例】 | 密闭场合与开阔场合的负反馈率对比 |
| §6 季节时段 | 社区投票=**使用惯例统计而非物理度量**【实证·弱】；置信度收缩【方法学】 | 反季提示命中时的采纳率与「不合场合」率 |
| §7 反馈校准 | **嗅觉适应【实证·中，全书最硬】**；聚合参数【假设】 | 本身即验证机制：校准生效后，同情境「刚好」占比应上升 |
| §8 表达规范 | 个体差异极大【实证·中】→ 反伪精确有科学基础 | 数字白名单拦截率（numguard 命中即 bug），文案 A/B |

**读这张表的正确方式**：右边一列不是"锦上添花的未来工作"，而是**这些规则唯一可能获得真实依据的途径**。文献能给的只有方向，给不了系数——没有任何研究把「重香惩罚乘数」映射到可测量的量。所以：

- 规则会改，依据只有两种：**自己的反馈数据**，或更硬的领域证据；
- **不要为了"更精确"去微调那些没有依据的系数**——把一个没依据的数换成另一个没依据但看起来更有出处的数，是退步不是进步；
- 更不要在代码注释、文档或 UI 里引论文给这些系数背书。方向可以说，量级不能装。

代码与手册不同步时，以代码为准，然后修手册。
