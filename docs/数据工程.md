# 数据工程

> 这篇文档讲一件脏活：一个 509 MB 的英文数据集，如何变成一个中文产品的数据底座。它不是氛寸最显眼的部分，却是最难被绕过的部分——推荐引擎再讲道理，数据进不来、搜不到、读不懂，一切归零。文中所有数字均实测于本仓库的构建产物与对原始数据的全量扫描（2026-07 复核），不是估算；文末的三条命令可以在你自己的机器上把它们全部重新算出来。

---

## 一、为什么是 ledecanteur：要社区投票，不要厂商宣称

氛寸的每条建议都要回答「为什么」。厂商文案回答不了——「前调佛手柑，优雅持久」是营销语言，不是决策依据。用香决策需要的是这瓶香水在大量真实身体上的表现分布：夏天有多少人觉得它合适，晚上呢，扩散到底有多冲。

ledecanteur（Fragrantica 社区数据）恰好是这个形状：

- **扩散 sillage**（1–4 均值）与**留香 longevity**（1–5 均值）——社区投票，不是实验室数据，但样本量够大时远比厂商宣称可信；
- **四季与日夜投票分布**——「这瓶适合夏天白天」在这里是几千人投出来的比例，不是一句话；
- **带强度的香调**（accords 0–100）与前中后调——规则引擎做风格判定的原料；
- **投票人数 people**——最重要的字段。它让每个统计量都带着自己的置信度，「不伪精确」才有落点：票太少的统计，我们敢于降级不用（见第四节）。

代价同样要说清：数据集全英文、以欧美社区为中心。观夏在里面有 23 款、闻献有 33 款，但气味图书馆一款都没有（实测检索为零）。这个数据集不是拿来就能用的——这正是本文其余部分存在的原因。

## 二、漏斗与分层：132,009 → 36,711 → 1,500 + 35,990

```text
ledecanteur/perfumes.jsonl          509 MB · 132,009 条 · 永不入库
  │
  │  npm run extract:terms          两遍流式扫描：people ≥ 50 → 按热度取 Top 1500
  ▼
.scratch/_selected.json             精选子集 + _terms.json 去重词表（供人工映射）
  │
  │  npm run build:data             应用 data/zh-map/ 四张映射表 + 预计算派生字段
  ▼
public/data/perfumes.min.json       主目录 1,500 款 · 全中文 · 随首屏加载
  │
  │  npm run build:ext              全量再扫描：(people ≥ 50 且不在 Top 1500) 或 国货
  ▼
public/data/ext-index.json          扩展集搜索索引 35,990 条 · 首次搜索才加载
public/data/ext/00..63.json         详情分片 64 个 · 点「入柜」才取
```

**第一刀：people ≥ 50，132,009 → 36,711。** 一条留香均值背后如果只有 3 个人投票，它不是统计，是轶事。阈值取 50 是在全量分布上实测后的平衡：≥30 有 46,486 款，≥100 有 25,126 款，≥200 只剩 16,056 款（另有 10,400 条 people 为空）。降到 30 会多出近万条低票长尾，统计噪声直接喂进推荐引擎；升到 100 会砍掉一万多款中腰部——其中很多真实躺在中国用户的香柜里。

**第二刀：分层，而不是二选一。** 36,711 款不能等量齐观地服务：

- **主目录（Top 1500）**是推荐引擎的工作集：按热度取前 1,500 款，逐款做中文精选，构建期预计算季节占比、日夜占比、扩散四档、风格标签——运行时零计算，gzip 262 KB 随首屏加载。
- **扩展集（35,990 款）**只为一件事存在：搜得到。它只进一个轻量搜索索引（每条五个短键字段，见第六节），详情按 `id % 64` 切成 64 个分片，用户点「入柜」时只取命中的那一片。

为什么不是二选一？全量 3.6 万款做全中文精选，人工不可行也无必要——头部之外的查询频次骤降；但只做 1,500 款，长尾就搜不到，而**香柜是推荐引擎的唯一输入**：用户那瓶进不了柜，产品对他就不成立。分层让绝大多数浏览只花 262 KB，同时 36,711 款每一瓶都进得来。

账目可以核对：36,711 − 1,500 = 35,211，加上国货白名单放行的 779 款低票记录，= 35,990，与 `ext-index.json` 条数严格一致（两层零交集，`build-ext.mjs` 用主目录 id 集合做排除）。

**派生口径只有一份。** `build.mjs`（主目录）与 `build-ext.mjs`（扩展集）共用 `scripts/derive.mjs` 的同一组纯函数：季节占比做拉普拉斯平滑（α = 5，几十票的季节分布不至于被抹成极端值）、sillage 四档（切点 1.75 / 2.5 / 3.25）、风格标签（按香调家族聚合加排除项判定，至多两个，兜底「日常百搭」）。同一瓶香不管落在哪一层，算出来的口径完全一致。

顺带一提工程形态：整条管线零 npm 依赖，只用 `node:fs` / `node:readline` / `node:zlib` 流式处理，内存有界，单机分钟级跑完。数据构建与应用构建彻底解耦——Vercel 构建机永远不需要碰那 509 MB。

## 三、中文化：四张映射表与一条保守原则

映射表在 `data/zh-map/`，全部是「英文原文 → 中文」的显式 JSON，人工与子代理翻译、逐张校对：

| 映射表 | 条目数 | 主目录实测覆盖 |
|---|---|---|
| `accords.json` 香调 | 99 | 主目录出现的 76 种香调全部有中文 |
| `notes.json` 气味词 | 845 | 788 个去重气味词，仅 1 个保留英文（Iso E Super——分子名，香圈通称就是它，映射表里显式原样保留） |
| `brands.json` 品牌 | 241 | 主目录全部 241 个品牌有映射（口径见下） |
| `names.json` 香名 | 1,500 | 1,335 款有中文名，89.0% |

指导原则只有一条：**错的中文名比英文更糟。** 英文名的代价是用户多打几个字母；错的中文名的代价是用户把别人家的香水加进香柜，下游的推荐、反馈、偏移全部建立在一个错误身份上。所以宁可回退，不硬翻。

这条原则落成了可核查的口径：

- **香名 89% 是分档的，不是一锅粥。** `names.json` 每条带 `source` 字段：`official` 544 款（官方或专柜通行名，如「蓝风铃」「大地」）、`literal` 752 款（无通行名时的忠实直译）、`nickname` 39 款（香圈绰号，如「无人区玫瑰」）——剩下 165 款标 `none`，诚实回退英文。另有 346 款带俗名别名（`aliases`），一并进搜索索引：搜「蓝风铃」能命中 Wild Bluebell，靠的是这张表，不是运气。
- **品牌「映射 100%」也要说诚实：不是 241 个都翻成了中文。** 有通行中文名的 120 个（香奈儿、祖玛珑、爱马仕……）；Byredo、Le Labo、Diptyque 这类小众品牌，香圈通行的称呼就是英文原名，硬造中文反而制造检索障碍——108 个原样保留；还有 13 个做的是英文规范化（Calvin Klein → CK、Lattafa Perfumes → Lattafa），把数据集里的注册全称改成用户真正会搜的写法。
- **覆盖率不是一句宣称，是每次构建重新算的数字。** 词表来自 `extract-terms.mjs` 第二遍扫描的副产品 `_terms.json`（按出现频次排序的去重词表）；`npm run build:data` 每次跑完打印四类中文覆盖率并列出未译词示例——数字掉了，构建日志先知道。

## 四、国货白名单：785 款里只有 6 款过票

做完 ≥50 票的第一刀，复查时发现一个系统性问题：中国品牌在这个以欧美社区为主的数据集里普遍低票。按「品牌串含汉字」识别（数据集里国货品牌是双语串，如 `To Summer | 观夏`、`DOCUMENTS 闻献`），全量共 785 款国货，**过 50 票的只有 6 款**：观夏三重茶（261 票）、颐和金桂（123）、空境研茶（58）、裸（57）、昆仑煮雪（56），以及六神花露水（56 票）。按统一阈值走，观夏 23 款只剩 5 款，闻献 33 款全军覆没。

决策不难做，因为用户画像清楚：这个产品的目标用户就在中国，他们的香柜里就有观夏和闻献。搜不到 = 进不了柜 = 产品对他不成立。所以 `build-ext.mjs` 的选取条件是：

```text
(people ≥ 50 且不在 Top 1500)  或  品牌串含汉字（国货，不设票数门槛）
```

**但放行不等于假装数据可信。** 779 款低票国货全部打上 `lowVotes: true`，推荐话术随之降级——推荐理由里会明说「这瓶的社区数据还少，判断偏保守，你的反馈会让它更准」（`src/lib/usage.ts`）。「不伪精确」不只是拦 LLM 编数字，也拦我们自己把 9 个人的投票当 9,000 人的投票用。

## 五、搜索：三层数据，一张榜单

搜索是这套分层数据的正门：「搜名秒加」是香柜的建立方式，搜索质量直接决定冷启动成败。数据有三层——主目录（1,500，全中文）、扩展集（35,990，英文为主）、手动记一瓶（两层都没有时的最后防线）。引擎是 MiniSearch 7，自定义分词：拉丁词整词、汉字逐字，中英混排都可检索；prefix + fuzzy 0.15，主目录字段权重中文名与别名（4）> 英文名（3）> 品牌（2）。

三层数据怎么合成一个搜索框，我们栽过两次真实的线上跟头。它们值得完整复盘，因为最终方案的每一条都对应一个真实教训。

### 事故一：「观夏」搜不到（PR #11）

- **现象**：用户搜「观夏」，一无所获。但观夏的 23 款明明就在扩展集里。
- **根因**：当时的逻辑是「主目录结果少于 3 条，才去查扩展集」。而主目录搜索是 OR + fuzzy——「观夏」被拆成「观」「夏」两个单字后，「夏」命中了主目录里的「卡夏尔」（Cacharel）系列。今天在同一索引上仍可复现：「观夏」在主目录返回 **7 条**命中，全部无关，其中 6 条是被单字「夏」凑数命中的卡夏尔。7 ≥ 3，兜底永远不触发。
- **修复**：扩展集不再是「触发式兜底」，每次查询两个索引都搜。当时的展示方式是把扩展集结果放进列表底部一个「更多结果 · 来自完整目录」的区隔里——这埋下了事故二。
- **教训**：在 OR + fuzzy 语义下，「主搜索结果稀少」不是可靠的触发条件。模糊搜索的天职就是宁滥勿缺，它几乎永远「不稀少」。兜底条件必须基于「有没有高质量匹配」，而不是「有没有匹配」。

### 事故二：「闻献」被折叠（PR #12）

- **现象**：修完事故一，真实用户搜「闻献」——结果确实在页面上，但在「更多结果」区隔里。用户看到上方几条无关命中，直接得出「没有」的结论，关掉了。
- **根因**：这次不是排序错了，是信息架构错了。按数据来源分区，等于把工程实现（两个索引）泄漏给用户，再要求用户用注意力替我们完成合并；「更多结果」这个标题甚至反向暗示上面已经没有匹配了。
- **修复**：取消区隔，两个索引的候选合并重排成一张榜单。
- **教训**：搜索结果不该按数据来源分区。「来自哪个索引」是实现细节，用户只关心「像不像我要找的」。信息架构的问题，不能转嫁给用户的注意力。

### 定案：rankSearchHits 统一排序

两条排序原则（产品定案，注释就写在 `src/lib/perfumes.ts` 的函数头上）：

1. **文本匹配档位优先**：查询整体命中名称（档 3）> 命中名称 + 品牌（档 2）> 仅模糊命中（档 1）。高度匹配的结果必须靠前，不许被任何别的信号淹没——「观夏」的品牌命中（几十票）必须压过 99,999 票的无关热门。
2. **同档位内按投票人数（主流度）**：同名多版本时，更常用的版本在前——搜「大地」，爱马仕主线压过各种衍生版。

实现是一个无 IO、无状态的纯函数 `rankSearchHits`，可以直接喂构造数据单测。工程细节：主目录候选取前 12、扩展集取前 50，按 id 去重后合并重排，榜单至多 9 条；扩展索引首次加载有延迟，所以先用主目录候选即时出结果，扩展候选到位后再合并重排，过期查询直接丢弃（`src/components/library/SearchAdd.tsx`）。

回归测试是双保险，针对的正是这两次事故的教训类型——「单元逻辑对，真实数据上错」：

- `src/lib/engine.test.ts` 用构造数据锁死档位与主流度规则的每个分支（垃圾热门不许上位、名称命中压品牌命中、同名按主流度、纯模糊仍给结果）；
- `src/lib/search.test.ts` 直接加载仓库里的真实构建产物（主目录 + 扩展索引共 3.7 万条）跑端到端：「观夏」「闻献」「昆仑煮雪」「大地」「蓝风铃」五个查询的榜首必须正确。

### 最后防线：手动记一瓶

1,500 + 35,990 之外的香（停产、自调、数据集整体缺失的品牌如气味图书馆）走 `ManualAdd`：填名字，从 13 个香调族里挑 1–3 个最像的，估一个扩散档。负数 id 保证永不与数据集冲突；没有社区数据就不假装有——留香话术自动落「因人而异」，季节四等分中性，靠之后的反馈收敛。「香柜是推荐引擎的唯一输入，每一瓶都进得来」，这句承诺的最后一块拼图在这里。

## 六、构建产物与体积（实测）

| 产物 | 内容 | 原始 | gzip |
|---|---|---|---|
| `public/data/perfumes.min.json` | 主目录 1,500 款，全字段 | 1.61 MB | 262 KB |
| `public/data/ext-index.json` | 扩展集搜索索引 35,990 条 | 2.3 MB | 748 KB |
| `public/data/ext/00..63.json` | 详情分片 64 个 | — | 最大单片 94.3 KB |

gzip 为 zlib 默认级别实测（2026-07 复核于仓库产物；`npm run build:ext` 每次构建会重新打印这组数字）。

扩展索引能压在这个体积，靠的是克制：每条只有 `{i, n, b, z?, p}` 五个短键字段——id、英文名、品牌、品牌中文（有才带，35,990 条里 10,214 条有）、票数，平均每条约 66 字节。这个索引的设计目标只有「能搜、能排序」，多一个字段都不进；详情字段全部留在分片里，点「入柜」才取。

加载策略与之配套：主目录随首屏；扩展索引第一次搜索才拉，此后内存缓存；详情按 `id % 64` 命中单片。`/data/*` 响应头是 `max-age=3600, stale-while-revalidate=86400`——路径不带版本号，所以不用 `immutable`，构建更新要在一小时内能被看见（`next.config.ts`）。

## 七、数据边界与许可

- **原始数据永不入库。** `.gitignore` 排除 `/ledecanteur/`，仓库只提交深度加工后的统计聚合产物。`extract-terms.mjs` 在第一步就丢弃 description、histogram、similar、ai_summary 等字段——不是「先都留着再说」，而是只保留推荐、卡片与解释所需的最小集合。
- **来源标注与许可切割。** 构建产物派生自 ledecanteur / Fragrantica 社区数据，版权归原始来源。仓库 README 明确声明：这部分数据仅作学习与展示用途，**不随代码一并按 AGPL-3.0-only 授权**，另作它用请自行核实来源许可。
- **重跑门槛即边界。** 想重跑管线，需要自己获取数据集——原始数据不随本仓库分发，这既是许可要求，也是 509 MB 不该进 git 历史的工程常识。

## 八、可复现性

本文的每个数字都不要求你信任我。自备 ledecanteur 数据集置于仓库根目录（`./ledecanteur/perfumes.jsonl`），然后：

```bash
npm run extract:terms  # 两遍流式扫描 → .scratch/_selected.json + 去重词表
npm run build:data     # 应用四张中文映射 + 预计算派生 → public/data/perfumes.min.json
npm run build:ext      # 全量扩展集 → ext-index.json + ext/00..63.json
```

三个脚本零 npm 依赖，Node 单机分钟级跑完。每一步都打印可核对的口径：`build:data` 打印四类中文覆盖率与未译词示例；`build:ext` 打印选入款数、国货与低票计数、索引及最大分片的 gzip 实测。改动任何管线代码后跑 `npm test`（38 例，含真实构建产物上的端到端搜索回归）——那是「观夏」与「闻献」两次事故留下的守门员。
