# 数据工程

> 一个 509 MB 的英文数据集，如何变成一个中文产品的数据底座。推荐引擎再讲道理，数据进不来、搜不到、读不懂，一切归零。

## 一、为什么是 ledecanteur：要社区投票，不要厂商宣称

氛寸的每条建议都要回答「为什么」。厂商文案回答不了：「前调佛手柑，优雅持久」是营销语言，不是决策依据。用香决策需要的是一瓶香在大量真实身体上的表现分布，ledecanteur（Fragrantica 社区数据）恰好是这个形状：

- **扩散 sillage**（1–4 均值）与**留香 longevity**（1–5 均值）：社区投票，样本量够大时远比厂商宣称可信；
- **四季与日夜投票分布**：「适合夏天白天」在这里是几千人投出来的比例；
- **带强度的香调**（accords 0–100）与前中后调：规则引擎做风格判定的原料；
- **投票人数 people**：最重要的字段。它让每个统计量带着自己的置信度，票太少的统计就降级不用（见第四节）。

代价要说清楚：社区均值是主观统计不是客观测量，数据集全英文、以欧美社区为中心——观夏在里面有 23 款、闻献有 33 款，气味图书馆一款都没有。

## 二、漏斗与分层

```text
ledecanteur/perfumes.jsonl       509 MB · 131,886 条可解析 · 永不入库
  │ npm run extract:terms        两遍流式扫描：people ≥ 50 → 按热度取 Top 1500
  ▼
.scratch/_selected.json          精选子集 + _terms.json 去重词表（供人工映射）
  │ npm run build:data           应用 data/zh-map/ 四张映射表 + 预计算派生字段
  ▼
public/data/perfumes.min.json    主目录 1,500 款 · 全中文 · 随首屏加载
  │ npm run build:ext            全量再扫描：(people ≥ 50 且不在 Top 1500) 或 brand 含汉字
  ▼
public/data/ext-index.json + ext/00..63.json    搜索索引 35,990 条 · 详情分片 64 个 · 懒加载
```

`extract-terms.mjs` 与 `build-ext.mjs` 流式读原始 JSONL，`build.mjs` 只读抽取后的精简文件。三个脚本都不在应用构建里跑——Vercel 构建机不碰那 509 MB。

**第一刀：people ≥ 50，筛出 36,711 条。** 一条留香均值背后只有 3 个人投票，那不是统计，是轶事。阈值 50 取自全量分布：≥30 有 46,486 款，≥100 有 25,126 款，≥200 只剩 16,056 款，另有 10,400 条 people 为空。降到 30 会把近万条低票长尾的统计噪声喂进推荐引擎；升到 100 会砍掉一万多款中腰部，其中很多真实躺在中国用户的香柜里。

**口径定死在这里。** 文件实际有 132,015 行（含 6 个空行），其中 **131,886 行能独立解析**——管线逐行流式解析（`readline` + `JSON.parse`，不做跨行拼接），拿到的就是这 131,886 条，筛出 **36,711** 条，构建产物的账目由此而来。剩下 123 行解析不了：源数据里有未转义的换行把记录劈开，这些换行落在 JSON 字符串内部、属非法控制字符，原样拼回仍然解析不了；先转义再拼能救回 22 段，收益不到 0.02% 的覆盖率，不值得为它给一条简单可靠的流式扫描引入状态机。所以「还原后总共有多少条」没有唯一答案，不作为口径使用。

**第二刀：分层。** 主目录（Top 1500）是推荐引擎的工作集：逐款做中文精选，构建期预计算好季节占比、日夜占比、扩散四档与风格标签，运行时零计算，gzip 后 249 KB 随首屏加载。

扩展集（35,990 款）只为「搜得到」而存在：每条只进一个轻量搜索索引（五个短键字段，见第六节），详情按 `id % 64` 切成 64 个分片，点「入柜」才取命中的那一片。

分层的理由很直接：全量 3.6 万款逐款中文精选不可行，而只做 1,500 款，长尾又进不了香柜。分层之后，绝大多数浏览只花 249 KB，同时 36,711 款每一瓶都搜得到。账目可核对：36,711 − 1,500 = 35,211，加上汉字品牌规则放行的 779 款低票记录 = 35,990，与 `ext-index.json` 条数一致。两层零交集，`build-ext.mjs` 用主目录 id 集合排除。

**派生口径只有一份。** `build.mjs` 与 `build-ext.mjs` 共用 `scripts/derive.mjs` 的同一组纯函数，同一瓶香不管落在哪一层，口径完全一致：

| 口径 | 函数 | 取值 |
|---|---|---|
| 投票均值清洗 | `voteAvg` | 低于量表下界一律 `null`（见第四节） |
| 季节占比 | `seasonPct` | 拉普拉斯平滑，`ALPHA = 5` |
| 日夜占比 | `daypartPct` | 归一；无票时 0.5 / 0.5 |
| 扩散四档 | `sillageTier` | 切点 1.75 / 2.5 / 3.25 |
| 风格标签 | `styleTags` | 按香调家族聚合加排除项判定，至多两个，兜底「日常百搭」 |

整条管线零 npm 依赖，只用 `node:fs` / `node:readline` / `node:zlib` 流式处理，内存有界，单机分钟级跑完。

**`popularity` 与 `priceValue` 刻意不进产出。** 两者在运行期一个字都没被读过（搜索排序用的是 `people`），却会随主目录进每一次首屏——实测占 54.0 KB raw / 12.5 KB gzip，而主目录是四页共用、在 `<head>` 里 preload 的关键路径资源。`popularity` 仍留在管线内部：`extract-terms` 靠它选 Top 1500、`build-ext` 靠它给分片排序，只是不写进文件（`derive.mjs:toPerfume`）。

## 三、中文化：四张映射表与一条保守原则

映射表在 `data/zh-map/`，全部是从英文原文到中文的显式 JSON。下表是本次构建实测，`npm run build:data` 每次跑完重新打印并列出未译词示例：

| 映射表 | 条目数 | 主目录覆盖 | 缺失时 |
|---|---|---|---|
| `accords.json` 香调 | 99 | 主目录出现的 76 种香调全部有中文 | 保留英文 |
| `notes.json` 气味词 | 845 | 788 个去重气味词，仅 Iso E Super 保留英文（分子名，香圈通称即英文） | 保留英文 |
| `brands.json` 品牌 | 241 | 主目录全部 241 个品牌有映射（口径见下） | 保留原品牌名 |
| `names.json` 香名 | 1,500 | 1,335 款有中文名（89.0%）：官方名 544 · 通行绰号 39 · 直译 752；余 165 款保留英文 | `nameZh` 为 `null`，展示英文名 |

指导原则只有一条：**错的中文名比英文更糟。** 英文名的代价是多打几个字母；错的中文名会让用户把别人家的香水加进香柜，下游的推荐与反馈全部建立在错误身份上。宁可回退，不为了抬覆盖率硬译。

- **香名分档。** `names.json` 以香水 id 为键，每条可带 `zh` / `aliases` / `source`。`source` 四取一：`official`（官方或专柜通行名，如「大地」）、`literal`（忠实直译，如「无人区玫瑰」）、`nickname`（香圈绰号，如「檀香33」）、`none`（回退英文），维护者据此判断可信度。另有 346 款带俗名别名一并进搜索索引：搜「爱马仕大地」能命中 Terre d'Hermès。
- **品牌分三类。** 有通行中文名的 120 个（香奈儿、祖玛珑、爱马仕……）；Byredo、Le Labo、Diptyque 这类小众品牌，香圈通行称呼就是英文原名，108 个原样保留；13 个做英文规范化，如 Calvin Klein 记作 CK、Lattafa Perfumes 记作 Lattafa。
- **扩展集不做逐款香名映射**（3.6 万款人工精选不可行）：`nameZh` 为 `null`、`aliases` 为空，但品牌、香调与气味词照样走共用映射。

## 四、汉字品牌补充规则

中国品牌在这个以欧美社区为主的数据集里普遍低票。数据集里国货品牌写成双语串，如 `To Summer | 观夏`、`DOCUMENTS 闻献`，所以识别方式就是「`brand` 含汉字」（`build-ext.mjs:hasCJK`）。照此统计，全量共 785 款，过 50 票的只有 6 款（观夏「三重茶」等）。按统一阈值走，观夏 23 款只剩 5 款，闻献 33 款为零。而目标用户就在中国，香柜里就有观夏和闻献。所以 `build-ext.mjs` 的选取条件是：`(people ≥ 50 且不在 Top 1500) 或 brand 含汉字（不设票数门槛）`。

**它是一条低票补充规则，不是国籍判断。** 判据只看字符，不看品牌注册地；把它当成「国货标记」去用，迟早会在别的用途上说错话。

放行不等于假装数据可信，两道防线：

- 其余 779 款低票记录全部标 `lowVotes: true`，推荐话术随之降级，理由里明说「这瓶社区数据还少，判断偏保守，你的反馈会让它更准」（`src/lib/usage.ts`）；
- 投票均值里的 `0` 一律判为「没有票」。量表下界是 1（rating/longevity/priceValue 1..5、sillage 1..4，见数据集随附的 `SCHEMA.md`），`0` 是缺票的哨兵值——而 `?? null` 只兜 null/undefined，挡不住落在合法类型内的哨兵：

  ```js
  voteAvg(v) => 有限数字且 v.average >= 1 ? v.average : null
  ```

  守卫统一放在 `derive.mjs:voteAvg`，`build-ext.mjs` 与 `extract-terms.mjs` 共用；单测「构建产物里不得出现 0 分」对主目录加全部 64 个分片全量校验。这道守卫护的主要就是这批低票记录：扩展集里 `longevity===0` 有 458 条、`sillage===0` 有 444 条，没有它，这些连一票留香数据都没有的香会被说成「散得偏快」，甚至拿到「贴身可闻 · 密闭也安全」这样的安全断言。

`null` 到了领域层各有各的降级口径（留香落「因人而异」、扩散落中间档但归因必须说明数据少、评分先验保持中性），见[领域规则手册 §2.4](领域规则手册.md#24-没有票不是-0-分)。

## 五、搜索：三层数据，一张榜单

「搜名秒加」是香柜的建立方式，搜索质量直接决定冷启动成败。数据有三层：主目录（1,500，全中文）、扩展集（35,990，英文为主）、手动记一瓶（最后防线）。引擎是 MiniSearch 7，自定义分词：拉丁词整词、汉字逐字，中英混排都可检索；开启 prefix 与 fuzzy 0.15。字段权重：主目录是中文名与别名（4）> 英文名（3）> 品牌（2）；扩展索引只索引英文名（3）、品牌与品牌中文（各 2）。

排序曾走过两个弯路，都由线上信号纠正（过程见[迭代实录](迭代实录.md)）。第一次：扩展集只在主目录结果少于 3 条时才查，而主目录用的是 OR 与 fuzzy 匹配，「观夏」拆成单字后命中 7 条无关结果（6 条是被「夏」字命中的卡夏尔），触发条件于是永远不成立——**用「主结果稀少」当兜底搜索的触发条件，在 OR + fuzzy 语义下不可靠**。第二次：并行检索后，扩展集结果被折叠在列表底部「更多结果 · 来自完整目录」的区隔里，用户以为上面就是全部。两次的修法都是去掉中间态：无条件并行检索，两层候选合并成一张榜单。

### rankSearchHits 统一排序

两条排序原则（注释写在 `src/lib/perfumes.ts` 函数头）：

1. **文本匹配档位优先**：整体命中名称（档 3）> 命中名称加品牌（档 2）> 仅模糊命中（档 1）。「观夏」的品牌命中必须压过票数再高的无关热门。
2. **同档位内按投票人数（主流度）**：搜「大地」，爱马仕主线压过各种衍生版。

实现是无 IO、无状态的纯函数 `rankSearchHits`：主目录候选取前 12、扩展集取前 50，按 id 去重后合并重排，榜单至多 9 条。扩展索引首次加载有延迟（建索引时 `addAllAsync` 分块让出主线程），所以先用主目录候选即时出结果，扩展候选到位后再合并重排，过期查询直接丢弃（`src/components/library/SearchAdd.tsx`）。扩展索引加载失败时保留主目录搜索，下次查询可重试。

回归测试两层：`src/lib/engine.test.ts` 用构造数据锁死档位与主流度规则的每个分支；`src/lib/search.test.ts` 加载真实构建产物（3.7 万条）跑端到端，「观夏」「闻献」「昆仑煮雪」「大地」「蓝风铃」五个查询的榜首必须正确。

两层都没有的香——停产、自调，或像气味图书馆这样数据集整体缺失的品牌——走 `ManualAdd` 手动记一瓶：填名字，从 13 个香调族里挑 1–3 个最像的，估一个扩散档。负数 id 保证永不与数据集冲突。没有社区数据就不假装有：留香话术自动落「因人而异」，季节四等分中性，靠之后的反馈收敛。

## 六、构建产物与加载

| 产物 | 内容 | 原始 | gzip |
|---|---|---|---|
| `public/data/perfumes.min.json` | 主目录 1,500 款，全字段 | 1.55 MB | 249 KB |
| `public/data/ext-index.json` | 扩展集搜索索引 35,990 条 | 2.37 MB | 748 KB |
| `public/data/ext/00..63.json` | 详情分片 64 个 | — | 最大单片 89.7 KB |

gzip 为 zlib 默认级别实测；后两行由 `npm run build:ext` 每次构建重新打印。扩展索引每条只有 `{i, n, b, z?, p}` 五个短键字段：id、英文名、品牌、品牌中文（35,990 条里 10,214 条有）、票数，平均每条约 66 字节。设计目标只有「能搜、能排序」；详情分片与主目录共用同一个 `Perfume` 形状。

加载策略与之配套：

- 主目录随首屏加载并缓存（`catalog.ts:loadCatalog`）；
- 扩展索引在搜索框获得焦点时就开始预热，此后内存缓存、失败可重试（`perfumes.ts:loadExtSearch`）；
- 详情按 `id % 64` 命中单片，整片缓存（`catalog.ts:fetchExtPerfume`）；
- `/data/*` 响应头是 `max-age=3600, stale-while-revalidate=86400`：路径不带版本号，所以不能用 `immutable`，构建更新一小时内可见（`next.config.ts`）。

## 七、数据边界与许可

- **原始数据永不入库。** `.gitignore` 排除 `/ledecanteur/` 与 `/.scratch/`，仓库只提交深度加工后的统计聚合产物。`extract-terms.mjs` 在第一步就丢弃 description、histogram、similar、ai_summary 等字段，只保留推荐、卡片与解释所需的最小集合。
- **来源标注与许可切割。** 构建产物派生自 ledecanteur / Fragrantica 社区数据，版权归原始来源。条款单列在 `LICENSES/LicenseRef-fragrance-data.txt`：这部分数据不随代码按 AGPL-3.0-only 授权，另作他用请自行核实来源许可。
- **改数据范围、字段或许可声明时，`REUSE.toml`、`THIRD-PARTY-NOTICES.md` 与 README 的许可段落要一起核。**

## 八、可复现性与验证

自备 ledecanteur 数据集置于仓库根目录（`./ledecanteur/perfumes.jsonl`），然后：

```bash
npm run extract:terms  # 两遍流式扫描 → .scratch/_selected.json + 去重词表
npm run build:data     # 应用四张中文映射 + 预计算派生 → public/data/perfumes.min.json
npm run build:ext      # 全量扩展集 → ext-index.json + ext/00..63.json
npm test               # 含真实构建产物上的端到端搜索回归
```

重建后至少核对这几条不变量（前四条已有单测覆盖）：

- 主目录与扩展集 id 零交集，两者条数与第二节的账目对得上；
- `ext-index.json` 的 id 与 64 个详情分片一一对应；
- `rating` / `longevity` / `sillage` 全库不出现 `0`；
- `lowVotes` 只出现在票数门槛外放行的记录上；
- `src/lib/search.test.ts` 的五个中英文与长尾查询榜首仍正确。
