# 数据工程

> 一个 509 MB 的英文数据集，如何变成一个中文产品的数据底座。推荐引擎再讲道理，数据进不来、搜不到、读不懂，一切归零。

## 一、为什么是 ledecanteur：要社区投票，不要厂商宣称

氛寸的每条建议都要回答「为什么」。厂商文案回答不了：「前调佛手柑，优雅持久」是营销语言，不是决策依据。用香决策需要的是一瓶香在大量真实身体上的表现分布，ledecanteur（Fragrantica 社区数据）恰好是这个形状：

- **扩散 sillage**（1–4 均值）与**留香 longevity**（1–5 均值）：社区投票，样本量够大时远比厂商宣称可信；
- **四季与日夜投票分布**：「适合夏天白天」在这里是几千人投出来的比例；
- **带强度的香调**（accords 0–100）与前中后调：规则引擎做风格判定的原料；
- **投票人数 people**：最重要的字段。它让每个统计量带着自己的置信度，票太少的统计就降级不用（见第四节）。

代价：数据集全英文、以欧美社区为中心。观夏在里面有 23 款、闻献有 33 款，气味图书馆一款都没有。

## 二、漏斗与分层：132,009 → 36,711 → 1,500 + 35,990

```text
ledecanteur/perfumes.jsonl       509 MB · 132,009 条 · 永不入库
  │ npm run extract:terms        两遍流式扫描：people ≥ 50 → 按热度取 Top 1500
  ▼
.scratch/_selected.json          精选子集 + _terms.json 去重词表（供人工映射）
  │ npm run build:data           应用 data/zh-map/ 四张映射表 + 预计算派生字段
  ▼
public/data/perfumes.min.json    主目录 1,500 款 · 全中文 · 随首屏加载
  │ npm run build:ext            全量再扫描：(people ≥ 50 且不在 Top 1500) 或 国货
  ▼
public/data/ext-index.json + ext/00..63.json    搜索索引 35,990 条 · 详情分片 64 个 · 懒加载
```

**第一刀：people ≥ 50，132,009 → 36,711。** 一条留香均值背后只有 3 个人投票，不是统计，是轶事。阈值 50 取自全量分布：≥30 有 46,486 款，≥100 有 25,126 款，≥200 只剩 16,056 款（另有 10,400 条 people 为空）。降到 30 会把近万条低票长尾的统计噪声喂进推荐引擎；升到 100 会砍掉一万多款中腰部，其中很多真实躺在中国用户的香柜里。

**第二刀：分层。** 主目录（Top 1500）是推荐引擎的工作集：逐款中文精选，构建期预计算季节占比、日夜占比、扩散四档、风格标签，运行时零计算，gzip 262 KB 随首屏加载。扩展集（35,990 款）只为「搜得到」存在：只进一个轻量搜索索引（每条五个短键字段，见第六节），详情按 `id % 64` 切成 64 个分片，点「入柜」才取命中的那一片。全量 3.6 万款逐款中文精选不可行；只做 1,500 款，长尾又进不了香柜。分层让绝大多数浏览只花 262 KB，同时 36,711 款每一瓶都搜得到。账目可核对：36,711 − 1,500 = 35,211，加上国货白名单放行的 779 款低票记录 = 35,990，与 `ext-index.json` 条数一致（两层零交集，`build-ext.mjs` 用主目录 id 集合排除）。

**派生口径只有一份。** `build.mjs` 与 `build-ext.mjs` 共用 `scripts/derive.mjs` 的同一组纯函数：季节占比拉普拉斯平滑（α = 5）、sillage 四档（切点 1.75 / 2.5 / 3.25）、风格标签（按香调家族聚合加排除项判定，至多两个，兜底「日常百搭」）。同一瓶香不管落在哪一层，口径完全一致。整条管线零 npm 依赖，只用 `node:fs` / `node:readline` / `node:zlib` 流式处理，内存有界，单机分钟级跑完；数据构建与应用构建解耦，Vercel 构建机不碰那 509 MB。

## 三、中文化：四张映射表与一条保守原则

映射表在 `data/zh-map/`，全部是「英文原文 → 中文」的显式 JSON：

| 映射表 | 条目数 | 主目录覆盖 |
|---|---|---|
| `accords.json` 香调 | 99 | 主目录出现的 76 种香调全部有中文 |
| `notes.json` 气味词 | 845 | 788 个去重气味词，仅 Iso E Super 保留英文（分子名，香圈通称即英文） |
| `brands.json` 品牌 | 241 | 主目录全部 241 个品牌有映射（口径见下） |
| `names.json` 香名 | 1,500 | 1,335 款有中文名，89.0% |

指导原则只有一条：**错的中文名比英文更糟。** 英文名的代价是多打几个字母；错的中文名会让用户把别人家的香水加进香柜，下游的推荐与反馈全部建立在错误身份上。宁可回退，不硬翻。

- **香名分档。** `names.json` 每条带 `source` 字段：`official` 544 款（官方或专柜通行名，如「蓝风铃」「大地」）、`literal` 752 款（忠实直译）、`nickname` 39 款（香圈绰号，如「无人区玫瑰」）、`none` 165 款回退英文。另有 346 款带俗名别名（`aliases`）一并进搜索索引：搜「蓝风铃」能命中 Wild Bluebell。
- **品牌分三类。** 有通行中文名的 120 个（香奈儿、祖玛珑、爱马仕……）；Byredo、Le Labo、Diptyque 这类小众品牌，香圈通行称呼就是英文原名，108 个原样保留；13 个做英文规范化（Calvin Klein → CK、Lattafa Perfumes → Lattafa）。
- **覆盖率每次构建重新算。** 词表来自 `extract-terms.mjs` 第二遍扫描的副产品 `_terms.json`；`npm run build:data` 每次跑完打印四类中文覆盖率并列出未译词示例。

## 四、国货白名单：785 款里只有 6 款过票

中国品牌在这个以欧美社区为主的数据集里普遍低票。按「品牌串含汉字」识别（数据集里国货品牌是双语串，如 `To Summer | 观夏`、`DOCUMENTS 闻献`），全量共 785 款国货，过 50 票的只有 6 款（观夏三重茶等）。按统一阈值走，观夏 23 款只剩 5 款，闻献 33 款为零。而目标用户就在中国，香柜里就有观夏和闻献。所以 `build-ext.mjs` 的选取条件是：`(people ≥ 50 且不在 Top 1500) 或 品牌串含汉字（国货，不设票数门槛）`。

放行不等于假装数据可信：其余 779 款低票国货全部标 `lowVotes: true`，推荐话术随之降级，理由里明说「这瓶的社区数据还少，判断偏保守，你的反馈会让它更准」（`src/lib/usage.ts`）。

## 五、搜索：三层数据，一张榜单

「搜名秒加」是香柜的建立方式，搜索质量直接决定冷启动成败。数据有三层：主目录（1,500，全中文）、扩展集（35,990，英文为主）、手动记一瓶（最后防线）。引擎是 MiniSearch 7，自定义分词：拉丁词整词、汉字逐字，中英混排都可检索；prefix + fuzzy 0.15；主目录字段权重中文名与别名（4）> 英文名（3）> 品牌（2）。

### 搜索排序的两次迭代

**第一次：扩展集从触发式改为无条件执行（PR #11）。** 最初扩展集只在主目录结果少于 3 条时才查。上线后的信号：搜「观夏」一无所获——主目录是 OR + fuzzy，「观夏」拆成单字后命中 7 条无关结果（6 条是被「夏」字命中的卡夏尔），「少于 3 条」永远不成立，扩展集里的观夏 23 款查不到。改法：取消触发条件，每次查询两个索引都搜。现状：扩展集与主目录并行检索，不设任何触发开关。

**第二次：取消分区，统一榜单（PR #12）。** 并行检索后，扩展集结果曾放在列表底部「更多结果 · 来自完整目录」的区隔里。用户反馈的信号：搜「闻献」，结果确实在页面上，但上方是几条无关命中，用户以为没有就关掉了。改法：取消分区，两个索引的候选合并重排成一张榜单——「来自哪个索引」是实现细节，用户只关心像不像要找的。现状即下述统一排序。

### rankSearchHits 统一排序

两条排序原则（注释写在 `src/lib/perfumes.ts` 函数头）：

1. **文本匹配档位优先**：整体命中名称（档 3）> 命中名称 + 品牌（档 2）> 仅模糊命中（档 1）。「观夏」的品牌命中必须压过 99,999 票的无关热门。
2. **同档位内按投票人数（主流度）**：搜「大地」，爱马仕主线压过各种衍生版。

实现是无 IO、无状态的纯函数 `rankSearchHits`：主目录候选取前 12、扩展集取前 50，按 id 去重后合并重排，榜单至多 9 条；扩展索引首次加载有延迟，先用主目录候选即时出结果，扩展候选到位后再合并重排，过期查询直接丢弃（`src/components/library/SearchAdd.tsx`）。回归测试两层：`src/lib/engine.test.ts` 用构造数据锁死档位与主流度规则的每个分支；`src/lib/search.test.ts` 加载真实构建产物（3.7 万条）跑端到端，「观夏」「闻献」「昆仑煮雪」「大地」「蓝风铃」五个查询的榜首必须正确。

两层都没有的香（停产、自调、数据集整体缺失的品牌如气味图书馆）走 `ManualAdd` 手动记一瓶：填名字，从 13 个香调族里挑 1–3 个最像的，估一个扩散档。负数 id 保证永不与数据集冲突。没有社区数据就不假装有：留香话术自动落「因人而异」，季节四等分中性，靠之后的反馈收敛。

## 六、构建产物与体积

| 产物 | 内容 | 原始 | gzip |
|---|---|---|---|
| `public/data/perfumes.min.json` | 主目录 1,500 款，全字段 | 1.61 MB | 262 KB |
| `public/data/ext-index.json` | 扩展集搜索索引 35,990 条 | 2.3 MB | 748 KB |
| `public/data/ext/00..63.json` | 详情分片 64 个 | — | 最大单片 94.3 KB |

gzip 为 zlib 默认级别实测，`npm run build:ext` 每次构建重新打印这组数字。扩展索引每条只有 `{i, n, b, z?, p}` 五个短键字段：id、英文名、品牌、品牌中文（35,990 条里 10,214 条有）、票数，平均每条约 66 字节。设计目标只有「能搜、能排序」；详情字段全部留在分片里，点「入柜」才取。

加载策略与之配套：主目录随首屏；扩展索引第一次搜索才拉，此后内存缓存；详情按 `id % 64` 命中单片。`/data/*` 响应头是 `max-age=3600, stale-while-revalidate=86400`：路径不带版本号，不用 `immutable`，构建更新一小时内可见（`next.config.ts`）。

## 七、数据边界与许可

- **原始数据永不入库。** `.gitignore` 排除 `/ledecanteur/`，仓库只提交深度加工后的统计聚合产物。`extract-terms.mjs` 在第一步就丢弃 description、histogram、similar、ai_summary 等字段，只保留推荐、卡片与解释所需的最小集合。
- **来源标注与许可切割。** 构建产物派生自 ledecanteur / Fragrantica 社区数据，版权归原始来源。仓库 README 声明：这部分数据仅作学习与展示用途，不随代码按 AGPL-3.0-only 授权，另作它用请自行核实来源许可。
- **重跑门槛即边界。** 原始数据不随本仓库分发，想重跑管线需自行获取数据集。

## 八、可复现性

自备 ledecanteur 数据集置于仓库根目录（`./ledecanteur/perfumes.jsonl`），然后：

```bash
npm run extract:terms  # 两遍流式扫描 → .scratch/_selected.json + 去重词表
npm run build:data     # 应用四张中文映射 + 预计算派生 → public/data/perfumes.min.json
npm run build:ext      # 全量扩展集 → ext-index.json + ext/00..63.json
```

三个脚本零 npm 依赖，Node 单机分钟级跑完。每步打印可核对的口径：`build:data` 打印四类中文覆盖率与未译词示例；`build:ext` 打印选入款数、国货与低票计数、索引及最大分片的 gzip 实测。改动管线代码后跑 `npm test`（38 例，含真实构建产物上的端到端搜索回归）。
